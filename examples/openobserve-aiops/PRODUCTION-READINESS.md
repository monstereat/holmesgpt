# Production Readiness Plan

Status: preparation only. This document describes the deployment inputs, configuration boundary, and acceptance gates for a later production environment. It does not configure a production account, create production credentials, apply migrations, or deploy services. The current Docker Compose file is a local test stack and must not be promoted as a production manifest.

## Target service layout

Keep the responsibilities already exercised in the local test environment:

| Service | Production responsibility | Deployment boundary |
| --- | --- | --- |
| Holmes API | Read-only AI investigation and approved observability tool calls | Private service endpoint; outbound model access through an approved egress policy |
| Incident API | Authenticated alert intake, identity, RBAC, incidents, approvals, retrospectives, audit | Behind the organization's TLS ingress and identity layer |
| Incident worker | Durable task delivery and bounded Holmes retries | Private worker pool with bounded concurrency and queue monitoring |
| PostgreSQL | Incidents, tasks, outbox, users/identity mapping, approvals, audit, retrospectives | Managed or operator-run HA database with tested backup and restore |
| Redis/Celery | Work queue and worker coordination | Private network only; PostgreSQL outbox remains the recovery source |
| OpenObserve | Logs, traces, RUM, and alert source | Use an edition/configuration with native RBAC, or retain a separately reviewed least-privilege query proxy |
| OpenObserve policy proxy | Narrow Holmes access to approved read-only streams/searches when required | Separate private network and dedicated read-only credentials; never expose arbitrary query or write routes |
| OpenTelemetry Collector | Receive application traces/metrics and forward through an authenticated, bounded telemetry path | Private OTLP receiver; authenticated backend exporter; bounded memory/batches and export retries |
| Business services | Emit telemetry and own their operational actions | Each service remains the owner of its action API; no Docker socket or arbitrary shell runner |

The Compose network names are local implementation details, not a production network design. Production network policy must explicitly allow only alert delivery, incident-to-worker calls, worker-to-Holmes calls, Holmes-to-policy-proxy queries, service-to-telemetry writes, database/broker traffic, and approved model egress.

### PostgreSQL identity bootstrap

[`postgresql-roles.psql`](postgresql-roles.psql) is a PostgreSQL-role template for a fresh application database. A database administrator runs it before the first migration; it creates `aiops_migrator`, `aiops_runtime`, and `aiops_worker`, grants schema creation only to the migrator, and grants the API runtime role DML plus sequence access on existing and future tables owned by the migrator. Migration `0006_audit_events_append_only` removes UPDATE, DELETE, and TRUNCATE on `audit_events` from the API runtime role and PUBLIC; runtime can still SELECT and INSERT audit events. Migration `0010_worker_database_privileges` grants the worker only the table reads and selected task/outbox column updates needed for delivery, plus audit inserts; the worker cannot access `users`, mutate incidents, or alter audit history. Configure role authentication through the selected secret manager or native database identity mechanism; the script contains no passwords. Feed the migration identity only to `MIGRATION_DATABASE_URL`, the API identity only to `DATABASE_URL`, and the worker identity only to `WORKER_DATABASE_URL`. In local Compose, `aiops` is reserved for bootstrap/finalize, `aiops_migrator` owns and applies schema changes, the API uses `aiops_runtime`, and the worker uses `aiops_worker`.

The API's `aiops_runtime` role retains UPDATE on `users`, including role/resource mapping fields, because the OIDC callback refreshes those fields from current IdP group claims. A holder of that API database credential can bypass the application authorization/audit path; this API database identity remains fully trusted and must be protected accordingly. The worker no longer shares that credential: migration `0010` gives `aiops_worker` narrowly scoped processing permissions and denies user-table access. This reduces the impact of worker credential/process compromise, but does not harden the API database identity against direct lifecycle mutation. Also, a request that authenticated before a disable transaction commits may finish; disable prevents later authentication but does not cancel already-authorized in-flight work.

The standalone bootstrap template does not transfer ownership of an already migrated schema. The local Compose bootstrap has a separate local-only ownership adoption step for the existing `aiops` test database; it transfers only public relations and schema ownership to `aiops_migrator` and skips table-owned sequences so PostgreSQL transfers those with their tables. This local step is not a managed-database migration procedure. Existing production databases need an owner-reviewed ownership/privilege adoption plan before using the migration role. Some managed PostgreSQL services restrict role creation or use IAM identities; use their supported role workflow and verify equivalent privileges. The template must be executed and permission-tested against a staging database before production use.

The release sequence, migration failure and rollback boundaries, and backup/restore procedure are documented in [`POSTGRESQL-OPERATIONS.md`](POSTGRESQL-OPERATIONS.md). The current isolated PostgreSQL checks establish repository behavior only; managed-service compatibility, encrypted off-host backups, PITR, measured RPO/RTO, and release rollback remain staging gates.

Re-run the isolated PostgreSQL 16 role and migration check with `bash examples/openobserve-aiops/verify-postgresql-roles.sh`. It starts a no-volume, no-port, no-network container with tmpfs data, applies all ten migrations, checks API runtime UPDATE grants for triage and user-lifecycle columns, checks worker task/outbox/audit access and denied user/incident/audit mutation, and verifies bootstrap reruns and denied schema creation. This verifies the repository role template; it does not replace testing the selected managed database's identity and privilege behavior.

- Run application containers as non-root, with a read-only root filesystem, all unnecessary Linux capabilities dropped, privilege escalation disabled, and only bounded writable temporary storage. Validate equivalent controls and writable paths on the selected platform.
- Terminate TLS at the approved ingress; expose only required API/UI routes. Keep worker, PostgreSQL, Redis, Holmes, proxy, and internal action-owner endpoints private.
- Use external secret references for database, session-signing, webhook, Holmes internal API, telemetry, proxy, model, and action-owner credentials. Define rotation and revocation procedures.
- Use OIDC authorization-code flow with PKCE S256, exact issuer and redirect-origin validation, one-time server-side state/nonce/verifier records, a short-lived HttpOnly session cookie, exact-origin checks for cookie-authenticated mutations, and explicit group-to-role/resource-scope mapping. Configure one trusted issuer per deployment. Test authorization on every mutating API, not only by hiding UI controls. Tenant isolation is not implemented by this example and must be supplied by the selected deployment and data model before multi-tenant use.
- Use separate runtime and migration database identities with least privilege. The API, worker, and migration runner reject non-local PostgreSQL URLs unless they explicitly use `sslmode=verify-full`; the local Compose stack opts into `AIOPS_ENV=local` and may use its isolated container network without TLS. The migration command requires `MIGRATION_DATABASE_URL` outside local mode and never falls back to the runtime `DATABASE_URL`. A transaction-scoped PostgreSQL advisory lock serializes concurrent migration jobs and releases automatically on commit or rollback. The runtime role cannot update/delete/truncate audit history after migration 0006. Review migrations, run them as a gated release step, and test rollback/forward recovery against a restored staging copy.
- Keep the Celery broker private. Outside local mode, the API and worker require `REDIS_URL` to use `rediss://`, include a password, set `ssl_cert_reqs=required`, and enable redis-py's `ssl_check_hostname=true`; this protects both the certificate chain and the broker hostname. The local Compose stack explicitly uses `AIOPS_ENV=local` and its isolated Redis network/AOF volume. Unit tests validate URL parsing, not a remote Redis TLS handshake; confirm the selected service's CA chain and authentication policy with a real TLS handshake before staging acceptance.
- Disable demo-only OpenObserve SSRF bypasses. Use native tenant/RBAC controls where available; otherwise document the residual trust placed in the read-only proxy and its credentials.
- Keep the Holmes tool path read-only, stream-scoped, time-bounded, size-bounded, and audited. Explicitly approve which telemetry may leave the environment for model inference.
- Treat the sample Holmes `max_steps: 12` as a per-investigation iteration cap only, not a monetary budget. Holmes records LiteLLM cost estimates after each completed call; zero/unknown estimates are omitted. A `/api/chat` timeout, transport failure, or HTTP 5xx now terminates the task as `holmes_outcome_unknown` without automatic retry, reducing duplicate charges when upstream completion is ambiguous; only explicit HTTP 429 is automatically retried. A worker lease expiring while the task is running is terminal `worker_outcome_unknown`, not an automatic retry; queued/outbox work is still re-enqueued. The retry API requires an explicit duplicate-charge acknowledgement for unknown outcomes; the workbench warns before sending it, and the append-only retry audit retains the original error code and acknowledgement. An authorized manual retry can still duplicate a charge. Before staging, configure a provider- or gateway-enforced project spend cap and alert, define the service response when the cap is reached, and verify those controls with the provider. The current direct DeepSeek integration's public API documents a balance lookup and `402` when funds are insufficient; that does not establish a configurable spending ceiling. Verify an enforceable cap in the selected account or place Holmes behind an approved budget-enforcing gateway. Do not treat estimated OpenTelemetry cost as an enforcement mechanism or invoice reconciliation.
- Keep production remediation disabled by default. The existing demo `set-chaos-mode` action now requires an explicit `AIOPS_DEMO_ACTIONS_ENABLED=true`; the application default is disabled. Add a production action only after its owner provides a narrow API, independent approval policy, idempotency key, postcondition, rollback behavior, and audit evidence.

Configure the selected broker's supported persistence/disk metrics and an alert, and test worker reconnection after a storage fault; the local Compose health check now verifies `aof_last_write_status=ok` in addition to `PING`.

## Release and rollback procedure

Use this procedure for a release rehearsal in staging first. It is platform-neutral: exact commands, rollout objects, traffic controls, and named operators must be added after the production platform and owners are selected. Do not execute it against production without a separately approved change window and go/no-go decision.

### Before the release window

1. Record the source revision, immutable image digests for every changed service, migration set, configuration/secret reference versions, release owner, database operator, rollback decision owner, and change window. Confirm the candidate was built and scanned by the approved pipeline; do not rebuild during promotion.
2. Confirm the previous known-good image digests and configuration references are still available. Review the application diff and every SQL migration. Classify schema changes as expand/contract; a release must not require an older application version to understand a newly destructive schema change.
3. Verify staging acceptance evidence, alert routing, on-call contacts, capacity headroom, and the selected rollback thresholds. Confirm production backup encryption, off-host retention, and restore access; take and validate a release-point backup using the platform-approved procedure. A successful local `pg_restore` rehearsal is not a production backup verification.
4. Freeze unrelated application/configuration changes for the window. Disable production remediation unless its service owner, approval boundary, idempotency, postcondition, and rollback have been explicitly accepted. Record baseline API errors/latency, queue depth/age, worker failures, and database health.

### Deploy and verify

1. Pause or drain alert intake only if the selected platform cannot safely handle the rollout; otherwise rely on the tested durable queue and admission limit. Do not discard queued work. Keep internal dependencies private.
2. Run the reviewed migration as a one-shot release job using the dedicated migration identity. Wait for a successful exit and verify the expected migration versions. Stop immediately on a migration error; do not start new application versions against an unknown schema state.
3. Roll out the telemetry proxy before Holmes and the worker. Wait for proxy health, then verify Holmes `/api/info?detail=full` reports the OpenObserve toolset as `enabled` with its expected tools before releasing workers or routing alerts. Roll out the incident API and workbench using immutable digests; keep worker concurrency and queue admission within staging-tested limits. Use readiness checks before routing traffic to each API replica.
4. Run smoke checks with synthetic or approved non-customer data: authentication and role denial cases, webhook idempotency, durable task completion, exact evidence links, audit writes, metrics scrape, and the approved read-only tool boundary. Confirm no test remediation can reach production-owned actions. After any proxy, Holmes, or worker restart, re-check the toolset gate before resuming alert traffic.
5. Compare against the pre-agreed thresholds for API errors/latency, oldest pending task age, failed tasks, worker retries, database health, and model/provider errors for the agreed observation window. Record image digests, migration versions, checks, dashboard snapshots, and the go/no-go decision. Resume any paused intake only after these checks pass.

### Roll back or contain

- Trigger rollback when a pre-agreed stop threshold is breached, a critical security boundary fails, data integrity is uncertain, or the release owner cannot establish service health. Stop rollout first; preserve logs, traces, audit events, and release identifiers.
- Roll back application images/configuration to the recorded previous digests and references in reverse dependency order. Keep the expanded, backward-compatible database schema in place. **Do not automatically run down migrations or delete data.** If the old application cannot safely run against the new schema, stop and use the rehearsed forward-fix path instead.
- If the worker or action owner may repeat side effects, pause dispatch/execution at the owning service and preserve queued tasks for inspection. Do not blindly replay tasks. Use the action owner's idempotency and reconciliation procedures, then verify external postconditions before resuming.
- If database corruption or loss is suspected, stop writes and follow the approved incident/data-recovery decision. Restore the validated backup or PITR recovery point into a separate database, verify migration state and business records, and obtain database/application-owner approval before changing the connection target. Never restore over the active database as an automatic rollback step; document the recovery point and acknowledged data-loss window.
- After rollback, verify readiness, authentication/RBAC, alert idempotency, worker/broker operation, queue age, audit continuity, read-only investigation boundaries, and customer-visible behavior. Keep the release contained until owners approve resumption; capture a timeline and root cause for the post-release review.

The target-specific runbook must replace these logical actions with reviewed commands, exact resources, health URLs, thresholds, observation duration, backup/PITR procedure, traffic controls, task-drain behavior, and owner contacts. Rehearse both an application rollback and a database restore/cutover in staging before production go-live.

## Staged acceptance plan

Each gate must have a named owner and retained evidence. Production data and actions are out of scope for staging acceptance unless separately approved.

| Gate | Acceptance evidence | Stop condition |
| --- | --- | --- |
| 1. Artifact and configuration | Image digests map to reviewed source; secret references resolve without printing values; no demo-only flags or public internal ports | Mutable image tags, missing secret owner, or `ZO_SKIP_SSRF_CHECKS` enabled |
| 2. Identity and authorization | OIDC login, tenant separation, viewer/operator/approver/admin matrix, self-approval rejection, API-level negative tests | Any cross-tenant read/write or requester self-approval |
| 3. Persistence and recovery | Reviewed migration on restored staging data; duplicate alert idempotency; worker/broker/database restart recovery; measured backup restore | Lost task/incident/audit data or untested recovery procedure |
| 4. Read-only investigation | Synthetic alert calls Holmes; tool traces show only approved read routes and streams; evidence links resolve; unsupported conclusions remain explicit | Any telemetry write, disallowed stream/query, secret leakage, or ungrounded release claim |
| 5. Workbench and approvals | Incident timeline, assignment/status, approval separation, reviewable retrospective, immutable audit events | UI-only authorization or untraceable state transition |
| 6. Action safety | Staging-only action owner; explicit allowlist; approved request; idempotent execution; verified postcondition; rollback test | Arbitrary shell/host access, missing approver, unverifiable state, or failed rollback |
| 7. Reliability and capacity | Load test establishes approved SLOs; worker duration, retries, persistent terminal-failure state, API saturation, and provider limits are observable | SLO not agreed, retry storm, unbounded queue, or missing cost guard |
| 8. Evaluation and release | Reproducible 20-case live report against synthetic staging evidence; per-case evidence/release matches; reviewed failure cases; rollback rehearsal | Mock report presented as model accuracy, missing per-case artifacts, or unreviewed regression |
| 9. Go/no-go | Security, data/privacy, operations, application, and action owners sign the evidence bundle; rollback and incident contacts are reachable | Any open critical finding, missing owner, or absent rollback decision |

The 20-case suite is a regression signal, not by itself proof of production readiness or an accuracy guarantee. [`evals/review_scoring.py`](evals/review_scoring.py) creates blinded reviewer sheets without reference answers and a separate answer key, validates per-case scores/evidence/reviewer notes/source identity, and compares two reviewer summaries while listing disagreements for adjudication; the machine-generated report remains `not_scored`. Keep the key sealed until two independent reviewers submit their sheets, then adjudicate disagreements and establish thresholds before using diagnosis scores as a release gate. Reviewer IDs in the sheets are audit fields, not proof that the reviewers are independent people.

The authenticated metrics endpoint reports API request counts, status-class labels, latency buckets, and in-flight requests per API process; these counters reset on process restart. Worker task p50/p95 duration is calculated from completed/failed tasks in the preceding 24 hours. Migration `0007_task_duration_metrics_index` adds a partial index to support that time-bounded query as task history grows. These timings include the Holmes call and are not provider-only latency or model cost. Metric labels use route templates, HTTP methods, and status classes; they omit user, incident, task, and alert identifiers.

### OIDC configuration contract

Set these values through the selected platform's runtime configuration and secret manager. This example contains placeholders only:

```text
AIOPS_ENV=production
AIOPS_AUTH_MODE=oidc
AIOPS_PUBLIC_ORIGIN=https://aiops.example.com
SESSION_SIGNING_KEY=<secret, at least 32 bytes>
SESSION_COOKIE_SECURE=true
AIOPS_OLDEST_PENDING_TASK_AGE_SLO_SECONDS=<owner-approved-seconds>
OIDC_ISSUER=https://identity.example.com/tenant
OIDC_METADATA_URL=https://identity.example.com/tenant/.well-known/openid-configuration
OIDC_CLIENT_ID=<registered-client-id>
OIDC_CLIENT_SECRET=<secret>
OIDC_REDIRECT_URI=https://aiops.example.com/auth/oidc/callback
OIDC_GROUP_MAPPINGS_JSON={"aiops-viewers":{"role":"viewer","resource_scopes":["order-service"]},"aiops-operators":{"role":"operator","resource_scopes":["order-service"]},"aiops-approvers":{"role":"approver","resource_scopes":["order-service"]}}
OIDC_GROUPS_CLAIM=groups
OIDC_SCOPES=openid profile email
```

The IdP must publish matching discovery metadata, support `S256`, issue a signed ID token with exact `iss`, `sub`, `aud`, `exp`, `iat`, and `nonce` claims, and supply the configured groups claim. This example has no break-glass/admin bootstrap path or role assignment UI; establish and document an operator recovery procedure before relying on OIDC for production access.
