## Target service layout

Keep the responsibilities already exercised in the local test environment:

| Service | Production responsibility | Deployment boundary |
| --- | --- | --- |
| Holmes API | Read-only AI investigation and approved observability tool calls | Private service endpoint; outbound model access through an approved egress policy |
| Incident API | Authenticated alert intake, identity, RBAC, incidents, approvals, retrospectives, audit | Behind the organization's TLS ingress and identity layer |
| Incident worker | Durable task delivery and bounded Holmes retries | Private worker pool with bounded concurrency and queue monitoring |
| PostgreSQL | Incidents, tasks, outbox, users/identity mapping, approvals, audit, retrospectives | Managed or operator-run HA database with tested backup and restore |

| OpenObserve policy proxy | Narrow Holmes access to approved read-only streams/searches when required | Separate private network and dedicated read-only credentials; never expose arbitrary query or write routes |
| OpenTelemetry Collector | Receive application traces/metrics and forward through an authenticated, bounded telemetry path | Private OTLP receiver; authenticated backend exporter; bounded memory/batches and export retries |
| Business services | Emit telemetry and own their operational actions | Each service remains the owner of its action API; no Docker socket or arbitrary shell runner |

The Compose network names are local implementation details, not a production network design. Production network policy must explicitly allow only alert delivery, incident-to-worker calls, worker-to-Holmes calls, Holmes-to-policy-proxy queries, service-to-telemetry writes, database/broker traffic, and approved model egress.

## Data durability and retention boundaries

These components hold different classes of state. A PostgreSQL backup does not
back up telemetry or the Collector queue, and Redis is not the business record
of whether an incident/task exists. Select retention and recovery objectives
with the relevant data owner; no duration or RPO/RTO is assumed here.

| Data | Authority and recovery boundary | Production decision before go-live |
| --- | --- | --- |
| Incidents, tasks, approvals, identity mappings, audit, retrospectives, outbox | PostgreSQL is authoritative. Recovery uses an encrypted off-host backup or PITR into an isolated target, then verifies schema, records, privileges, and service readiness. | HA/failover, backup frequency, retention/deletion, PITR window, restore owner, measured RPO/RTO, and audit/evidence access policy. |
| Celery/Redis messages | Redis carries execution messages; persisted PostgreSQL task and outbox rows remain available for dispatch reconciliation. Redelivery may create duplicate broker messages, while database task claiming prevents duplicate task execution. | Broker durability/AOF or managed persistence, recovery behavior, max queue storage, task/outbox retention, alert routing, and queue age objective. |
| OpenObserve logs, traces, RUM, and alert-source telemetry | Stored by the selected OpenObserve service/storage and not covered by the PostgreSQL backup. Holmes investigation evidence persisted in task results is separately within the PostgreSQL recovery boundary. | OpenObserve edition/tenant model, retention/deletion, storage encryption, backup/export and restore process, access review, telemetry loss window, and data residency. |
| OpenTelemetry Collector export queue | The production template uses a bounded file-backed queue. A persistent volume can preserve queued telemetry across Collector restarts, but loss/fullness of that volume or expiration of export retries can lose telemetry; PostgreSQL backups do not include it. | Encrypted persistent storage, capacity and retry window from measured load, volume backup/restore or accepted loss policy, filesystem monitoring, and Collector extension support status. |
| Live evaluation reports and human-review records | Evaluation reports are artifacts, not operational state. The generated review sheets, answer keys, scores, adjudication, and report hashes must remain separately access-controlled and traceable to the exact run. | Repository/artifact retention, reviewer identity and independence, access to answer keys, and evidence-retention duration. |

Do not claim that PostgreSQL backup protects the monitoring history or Collector
spool. Staging must rehearse recovery for every data class the service owner
requires to survive, and explicitly record which telemetry loss is accepted.

The local Compose stack intentionally uses some plaintext HTTP between containers and a broad shared `app` network to support its test harness. Do not infer production reachability from that network or reuse it as a production segmentation design. At minimum, Holmes must not have a route to OpenObserve except through the policy proxy, and the order-service demo's database reachability must not be copied into a production business-service topology.

### PostgreSQL identity bootstrap

[`postgresql-roles.psql`](postgresql-roles.psql) is a PostgreSQL-role template for a fresh application database. A database administrator runs it before the first migration; it creates `aiops_migrator`, `aiops_runtime`, `aiops_worker`, and the `aiops_break_glass NOLOGIN` custodian group, grants schema creation only to the migrator, and grants the API runtime role SELECT/INSERT/UPDATE plus sequence access on ordinary existing and future tables owned by the migrator. For `users`, it revokes table-level INSERT/UPDATE and grants only the columns needed by current local seed, OIDC synchronization, and user lifecycle routes once the full identity schema exists; migration `0016_restrict_runtime_user_columns` applies the same ACL after upgrades. When upgrading from migration 0012, the database administrator must rerun this template before migration 0013; 0013 aborts if the shared recovery role can still log in. Migration `0006_audit_events_append_only` removes UPDATE, DELETE, and TRUNCATE on `audit_events` from the API runtime role and PUBLIC; runtime can still SELECT and INSERT audit events. Migration `0010_worker_database_privileges` grants the worker only the table reads and selected task/outbox column updates needed for delivery, plus audit inserts; the worker cannot access `users`, mutate incidents, or alter audit history. Migration `0011_restrict_runtime_delete` removes API DELETE on business tables and allows it only on expiring OIDC login transactions and revoked session records, which the API prunes/consumes. Migrations `0012` and `0013_two_person_admin_recovery` leave the custodian group with function execution only; individually authenticated database identities must be provisioned as members, and PostgreSQL rejects approval when `session_user` matches the requester. Configure identity mapping through the selected secret manager or native database mechanism; the script contains no passwords. Feed the migration identity only to `MIGRATION_DATABASE_URL`, the API identity only to `DATABASE_URL`, and the worker identity only to `WORKER_DATABASE_URL`. Do not use a shared break-glass login. In local Compose, `aiops` is reserved for bootstrap/finalize, `aiops_migrator` owns and applies schema changes, the API uses `aiops_runtime`, and the worker uses `aiops_worker`.

The API's `aiops_runtime` role no longer has table-level INSERT/UPDATE on `users`; migration `0016` limits it to specific columns used by local seed, OIDC synchronization, and lifecycle routes, while blocking changes to OIDC issuer/subject and creation timestamps. This narrows accidental and SQL-injection write surface but does not make identity authorization independent of the API: runtime still needs to insert identities and update role/resource scopes from verified IdP claims, and a holder of the database credential can abuse those permitted columns. Treat the API identity as trusted and protect it accordingly; a stronger boundary requires separately operated identity provisioning/group synchronization. Its DELETE privilege is limited to expiring login transactions and revoked sessions. The worker uses a separate credential: migration `0010` gives `aiops_worker` narrowly scoped processing permissions and denies user-table access. Also, a request that authenticated before a disable transaction commits may finish; disable prevents later authentication but does not cancel already-authorized in-flight work.

OIDC identity provisioning and changes to claim-derived username, role, or resource scopes append `user.provisioned` / `user.claims_synchronized` audit events in the same database transaction as the user write. Routine sign-ins with unchanged claims do not create audit rows. The event records changed field values, not raw tokens or group claims. This implementation has not been functionally verified; test transaction rollback and audit readability before relying on it operationally.

The standalone bootstrap template does not transfer ownership of an already migrated schema. The local Compose bootstrap has a separate local-only ownership adoption step for the existing `aiops` test database; it transfers only public relations and schema ownership to `aiops_migrator` and skips table-owned sequences so PostgreSQL transfers those with their tables. This local step is not a managed-database migration procedure. Existing production databases need an owner-reviewed ownership/privilege adoption plan before using the migration role. Some managed PostgreSQL services restrict role creation or use IAM identities; use their supported role workflow and verify equivalent privileges. The template must be executed and permission-tested against a staging database before production use.

The release sequence, migration failure and rollback boundaries, and backup/restore procedure are documented in [`POSTGRESQL-OPERATIONS.md`](POSTGRESQL-OPERATIONS.md). The current isolated PostgreSQL checks establish repository behavior only; managed-service compatibility, encrypted off-host backups, PITR, measured RPO/RTO, and release rollback remain staging gates.

Run the isolated PostgreSQL 16 role and migration check with `bash examples/openobserve-aiops/verify-postgresql-roles.sh` when the role template changes. It starts a no-volume, no-port, no-network container with tmpfs data, applies every repository migration (currently `0001`–`0021`), checks API runtime column-level INSERT/UPDATE grants on `users` plus triage and user-lifecycle columns, verifies API DELETE is limited to expiring OIDC login transactions and revoked sessions, and checks worker task/outbox/audit/action-execution access, confirms migration 0019 grants the dead-letter column update to `aiops_runtime` and denies it to `aiops_worker`, and checks the migration ledger through 0021 plus the active-task, task-metrics, and outbox-metrics indexes. It creates two custodian logins and verifies request creation, requester self-approval denial, successful approval by a different authenticated session, identity audit, denial when an admin is active, and absence of direct table grants. It also verifies bootstrap reruns and denied schema creation. On 2026-09-29, this verifier passed against all 21 migrations. This verifies the repository role template; it does not replace testing the selected managed database's identity mapping and privilege behavior.

### Secret rotation and revocation

Use this sequence for every production credential. Keep the platform-specific secret-manager commands, reference names, owners, and emergency contacts in the deployment's companion runbook; never put credential values in tickets, shell history, command output, or logs.

1. Inventory the credential owner, consumers, secret reference/version, expiry, and revocation method. Include every API replica, worker, migration job, sender, scraper, and external service that uses it.
2. Create a replacement with the same or narrower permissions in the approved secret manager. Record its version identifier, not its value, and confirm the intended consumers can read it.
3. For either webhook, use its `_PREVIOUS` variable as the single overlap slot. First deploy the new token in the previous slot while every API replica still has the old active token; after all replicas accept both, switch the sender to the new value. Then promote the new value to the active variable and put the old value in the previous slot, roll all API replicas, verify deliveries, and clear the previous slot. At every stage, replicas accept the sender current token; keep the two active webhook secrets distinct. For Alertmanager, an unset `ALERTMANAGER_WEBHOOK_TOKEN` keeps the route disabled even if its previous slot is populated. `SESSION_SIGNING_KEY` still has one active key; rotating it invalidates existing signed sessions and requires users to sign in again.
4. Update only the owning consumers through the selected platform's supported rollout/reload process. For database and Redis credentials, rotate the distinct API, worker, and migration identities separately, then recycle their connection pools so validation proves a fresh connection uses the replacement.
5. Verify readiness and one synthetic authentication or connection check for each consumer. Confirm stale credentials are rejected where the integration permits a safe check; inspect only status codes and credential version identifiers.
6. Revoke the previous credential after all consumers have reloaded and passed verification. For a suspected compromise, revoke immediately, contain affected traffic, issue a replacement, and accept temporary unavailability rather than retaining a known-exposed credential.
7. Record the change reference, secret version identifiers, consumers verified, revocation time, and any forced reauthentication or delivery interruption. If the new credential fails before the old one is revoked, restore the previous secret reference; after revocation, issue another replacement instead of re-enabling the revoked value.

Production acceptance requires a rehearsal with the selected secret manager and service rollout process. The generic sequence does not establish provider-side dual-version support, rotation APIs, secret access audit delivery, or a zero-downtime window.

## Release and rollback procedure

Use this procedure for a release rehearsal in staging first. It is platform-neutral: exact commands, rollout objects, traffic controls, and named operators must be added after the production platform and owners are selected. Do not execute it against production without a separately approved change window and go/no-go decision.

### Before the release window

1. Record the source revision, immutable image digests for every changed service, migration set, configuration/secret reference versions, release owner, database operator, rollback decision owner, and change window. Confirm the candidate was built and scanned by the approved pipeline; do not rebuild during promotion.
2. Confirm the previous known-good image digests and configuration references are still available. Review the application diff and every SQL migration. Classify schema changes as expand/contract; a release must not require an older application version to understand a newly destructive schema change.
3. Verify staging acceptance evidence, alert routing, on-call contacts, capacity headroom, and the selected rollback thresholds. Confirm production backup encryption, off-host retention, and restore access; take and validate a release-point backup using the platform-approved procedure. A successful local `pg_restore` rehearsal is not a production backup verification.
4. Freeze unrelated application/configuration changes for the window. Disable production remediation unless its service owner, approval boundary, idempotency, postcondition, and rollback have been explicitly accepted. Record baseline API errors/latency, queue depth/age, worker failures, and database health.

### Deploy and verify

1. Pause or drain alert intake only if the selected platform cannot safely handle the rollout; otherwise rely on the tested durable queue and admission limit. Do not discard queued work. Keep internal dependencies private.
2. Run the reviewed migration as a one-shot release job using the dedicated migration identity. Wait for a successful exit and verify the expected migration versions. Stop immediately on a migration error; do not start new application versions against an unknown schema state.
3. Roll out the telemetry proxy before Holmes and the worker. Wait for proxy health, then verify Holmes `/api/info?detail=full` reports the OpenObserve toolset as `enabled` with its expected tools before releasing workers or routing alerts. Roll out the incident API and workbench using immutable digests; keep worker concurrency and queue admission within staging-tested limits. Use readiness checks before routing traffic to each API replica.
4. Run smoke checks with synthetic or approved non-customer data: authentication and role denial cases, webhook idempotency, durable task completion, exact evidence links, audit writes, metrics scrape, and the approved read-only tool boundary. Confirm no test remediation can reach production-owned actions. After any proxy, Holmes, or worker restart, re-check the toolset gate before resuming alert traffic.
5. Compare against the pre-agreed thresholds for API errors/latency, oldest pending task age, failed tasks, worker retries, database health, and model/provider errors for the agreed observation window. Record image digests, migration versions, checks, dashboard snapshots, and the go/no-go decision. Resume any paused intake only after these checks pass.

### Roll back or contain

- Trigger rollback when a pre-agreed stop threshold is breached, a critical security boundary fails, data integrity is uncertain, or the release owner cannot establish service health. Stop rollout first; preserve logs, traces, audit events, and release identifiers.
- Roll back application images/configuration to the recorded previous digests and references in reverse dependency order. Keep the expanded, backward-compatible database schema in place. **Do not automatically run down migrations or delete data.** If the old application cannot safely run against the new schema, stop and use the rehearsed forward-fix path instead.
- If the worker or action owner may repeat side effects, pause dispatch/execution at the owning service and preserve queued tasks for inspection. Do not blindly replay tasks. Use the action owner's idempotency and reconciliation procedures, then verify external postconditions before resuming.
- If database corruption or loss is suspected, stop writes and follow the approved incident/data-recovery decision. Restore the validated backup or PITR recovery point into a separate database, verify migration state and business records, and obtain database/application-owner approval before changing the connection target. Never restore over the active database as an automatic rollback step; document the recovery point and acknowledged data-loss window.
- After rollback, verify readiness, authentication/RBAC, alert idempotency, worker/broker operation, queue age, audit continuity, read-only investigation boundaries, and customer-visible behavior. Keep the release contained until owners approve resumption; capture a timeline and root cause for the post-release review.

The target-specific runbook must replace these logical actions with reviewed commands, exact resources, health URLs, thresholds, observation duration, backup/PITR procedure, traffic controls, task-drain behavior, and owner contacts. Rehearse both an application rollback and a database restore/cutover in staging before production go-live.

### Metrics scan bound and owner decision

Migration `0021_metrics_scan_indexes` does not make every metrics query bounded. `aiops_tasks` and `aiops_task_retry_attempts_total` retain exact counts across all task rows and scan the covering `(status) INCLUDE (attempt)` index; work therefore grows linearly with retained task history. `aiops_outbox_dead_lettered_events` similarly counts every retained dead-letter row through its partial index and grows with retained dead letters. A covering or partial index can reduce row width and heap access, but does not bound the number of index entries examined. By contrast, task duration is restricted to the last 24 hours, pending age uses the active-task partial index, and eligible outbox dispatch metrics start from queued/retrying tasks with the configured pending-task cap. Those query shapes do not resolve the two historical totals above.

Do not silently add a time predicate to the existing full-history metrics: it would change their meaning, and `aiops_task_retry_attempts_total` is a Prometheus counter whose name/semantics must remain monotonic. The smallest semantics-preserving direction is a transactional summary updated in the same database transaction as each task status/attempt change and dead-letter transition, with metrics reading the compact summary. That requires a new schema migration, a one-time backfill/reconciliation plan, tightly scoped runtime grants, and staging checks for summary-row contention and upgrade duration. It must not be introduced as a source-only optimization because a missed transition would make durable operational metrics inaccurate.

The data/operations owner must choose one of these contracts before implementation:

1. **Keep exact lifetime totals:** add a transactionally maintained summary for task status counts, retry attempts, and dead-letter count. Preserve task/evidence rows under a separately approved retention policy; define summary reconciliation and counter behavior if records are later deleted.
2. **Bound retained history and change metrics scope:** approve task/result/audit and dead-letter retention duration plus any hard cardinality/partition cap; rename or explicitly version the affected metrics as retained-window values, including a valid Prometheus counter contract for retry totals. Confirm which incident/task evidence the workbench may lose when cleanup runs.
3. **Accept the current scans:** set a maximum retained row count and metrics scrape/database latency budget, and require staging measurements at that maximum before release. Without a row-count bound this is an operational assumption, not a strict query bound.

Decision required: select the metric contract, task/evidence and dead-letter retention, expected maximum retained cardinality, and acceptable scrape/query latency. Until then, keep the existing metric semantics and SQL unchanged; do not claim that migration `0021` bounds full-history scans.

Both webhook routes stream request bodies through a 64 KB hard limit before JSON parsing; requests without `Content-Length` are accepted only when the streamed body stays within that limit. Every configured token, including a previous-token overlap value, must contain at least 32 UTF-8 bytes outside local mode. Keep the two webhook token families distinct, deliver each value through its own secret reference, and use the overlap-slot rollout above; never print token values during verification.

The IdP must publish matching discovery metadata, support `S256`, issue a signed ID token with exact `iss`, `sub`, `aud`, `exp`, `iat`, and `nonce` claims, and supply the configured groups claim. Register the callback URI exactly. This example has no role assignment UI; establish and document an operator recovery procedure before relying on OIDC for production access.

### Administrator bootstrap and lockout recovery

The application accepts `admin` as an OIDC-mapped role. The first active administrator is created only when an authenticated identity signs in with an IdP group that maps to `{"role":"admin","resource_scopes":[...]}`; there is no built-in default account or password fallback outside local mode. A `resource_scopes` value of `"*"` grants incident access across every resource and cannot be combined with specific scopes; reserve it for explicitly approved global operators. The `admin` role grants global user-mapping management; service resource scopes limit incident access and do not narrow that global identity-administration permission. Before staging, configure a dedicated, tightly controlled administrator group and map it only to the minimum service scopes needed for incident operations. Assign at least two distinct named custodians in the IdP and verify both can sign in; do not use a shared account. Keep their IdP recovery process separate from this application.

Disabling one administrator is rejected when that would remove the last active administrator. Re-enabling a disabled identity through the application requires an existing active administrator to approve its OIDC reactivation request. The repository includes [`alert-trigger/break_glass_admin.py`](alert-trigger/break_glass_admin.py) for the all-admins-disabled case. Migration `0013_two_person_admin_recovery` installs request and approval functions owned by the migration role; `aiops_break_glass` is `NOLOGIN` and has only function execution, with no direct table access. One individually authenticated custodian login creates an audited request; a different custodian must authenticate through a separately provisioned database identity and approve it. PostgreSQL compares the actual `session_user` values, so caller-supplied names cannot satisfy the dual-control check. The approval step also requires out-of-band confirmation that the target remains in the IdP admin group. The function rechecks total admin lockout and the disabled target under an exclusive lock, then reactivates only that existing admin, increments session generation, completes the request, and writes the audit event in one transaction. It never creates an account or changes the target role/resource scopes.

All transactional authenticated write routes now revalidate the presented session inside the business transaction while holding the session advisory lock and a row lock on the active user. Logout uses the same session-lock order before recording revocation. User disable/reactivation and OIDC claim synchronization also take a shared lifecycle advisory lock before identity or user-row changes. Thus concurrent application lifecycle operations serialize, and revocation and a write serialize at the database boundary: a write that acquired its lock first may finish before revocation commits; a request acquiring it afterward is rejected. The IdP remains authoritative for role mappings. Removing the last administrator from the IdP group can demote that account and leave no active application administrator until an IdP-mapped replacement signs in; the database break-glass path only restores an existing disabled administrator and cannot reverse IdP role demotion. Keep at least two named IdP custodians and rehearse replacement-admin sign-in in staging. An isolated PostgreSQL `aiops_test` case passed for OIDC claim synchronization racing with account disable: the operations serialize, claim synchronization completes, disable remains effective, and the session generation advances. Other identity-lifecycle interleavings and behavior with a real organization IdP remain unverified. Approval actions now have a separate durable execution record and resumable owner-idempotent path; the focused 2026-09-29 isolated check passed recovery from persisted `dispatching` and `rollback_pending` phases. Concurrent identity changes beyond the selected case, process-kill timing windows, automatic stale-action reconciliation, and production readiness remain unverified.

The per-custodian DSN must come from the target platform's secret manager and must not be a runtime, worker, or migration credential. Provision an individually authenticated database principal for each custodian and grant each only membership in `aiops_break_glass`; do not give the group role LOGIN or use a shared login. Keep access disabled except during an approved recovery, constrain it to the required database, and independently review every use. Rehearse both stages in staging:
