# 本机 Docker 测试环境的 AIOps 事故诊断与受控处置平台

## 背景与目标

- 背景：仓库已有 OpenObserve Toolset、NestJS 订单故障源、Python 告警接收器和本地 Compose 演示；接收器使用 `/bin/echo` 替代 Holmes，任务状态仅驻留内存，尚无真实调查结果和重启恢复。
- 目标：先在当前电脑的 Docker 测试环境中，把项目主要功能做成可运行、可恢复、可验收的闭环；同时整理后续正式环境部署所需的边界和待确认项。本目标不连接或部署到正式生产环境。
- 成功标准：本机可启动身份校验、告警去重、持久事故与任务、可靠调查、真实 Holmes/OpenObserve live 调查、事故工作台、测试环境审批和受限处置、执行后验证/回退、复盘及可重复评测；测试结果明确区分 mock 与 live。live 凭据或端点缺失时，相应切片和完整验收保持阻塞/未完成，不以 mock 结果代替。

## 范围

- 包含：扩展现有 Python/FastAPI Holmes API；在本地 Docker Compose 中运行事故/任务持久化和可靠队列；本地身份/RBAC；Holmes 对 OpenObserve 的只读调查；发布/CI 与 Runbook 的本地接口/fixture；事故工作台；审批；仅作用于演示订单服务的白名单测试动作；执行后验证、可控回退、审计、复盘；20 例离线/可回放评测；本地启动、备份恢复和演示文档；记录后续正式环境的部署差异与未决决策。
- 不包含：连接真实生产凭据或生产观测平台；发布到正式生产；修改真实业务资源；无审批的 Agent 写操作；模型直接持有执行凭据；访问 Docker socket 或允许任意 Shell 命令；尚未逐项定义和授权的正式环境处置动作。
- 建议实现边界（Plan 阶段按仓库实际结构确认）：Holmes 调查/API 继续使用 Python/FastAPI；NestJS 保留为订单演示服务和仅供测试的动作拥有方；PostgreSQL 保存事故/任务元数据；Redis + Celery 是可靠队列候选；OpenObserve 保存日志/Trace。数据库 schema/migration 仍须单独获得用户明确授权后才可实施。

## 用户与行为

### AC-01：告警安全接收和幂等去重

- 前置条件：本机 Compose 服务启动，测试 webhook token 通过运行时环境注入。
- 操作：提交合法、重复、未认证和字段超限的告警。
- 预期结果：合法告警创建或复用稳定事故/任务；重复请求返回相同标识；未认证或无效请求拒绝且不排队。
- 验证方式：API 单测与本地集成测试。

### AC-02：事故和任务跨重启恢复

- 前置条件：用户已单独授权本地测试数据库 schema/migration 并完成初始化。
- 操作：创建任务、重启 API 或 worker，再查询任务并继续未完成任务。
- 预期结果：事故关联、状态、尝试次数、时间线和已完成结果持久化；未完成任务可安全恢复，不重复创建事故。
- 验证方式：PostgreSQL 集成测试和本机 Compose 重启验收。

### AC-03：调查具有有界重试和明确终态

- 操作：让隔离的 mock Holmes 调用分别成功、瞬时失败、超时和永久失败。
- 预期结果：瞬时错误按有界退避重试；达到上限后进入失败终态；重复投递幂等；错误输出不泄露 token、密钥或敏感 stderr。
- 验证方式：worker 单测和任务状态集成测试。

### AC-04：Holmes 只读调查保留证据

- 前置条件：完整本机验收需要用户在运行环境提供模型凭据、OpenObserve 地址、只读凭据和流白名单；未具备时 AC-04 保持阻塞，不能以 mock 结果完成整体验收。
- 操作：调查可复现的订单 HTTP 500。
- 预期结果：调查结论记录时间范围及可复查的日志/Trace 证据；无法证明的说法标为假设；查询范围受限且调查工具无写权限。
- 验证方式：mock 仅验证错误、超时、重试和结果格式；必须另做本机 live 端到端验收，分别记录两种结果。

### AC-05：本机事故工作台显示完整进度

- 操作：打开本机工作台并查看待处理、调查中、成功、失败和待审批事故。
- 预期结果：显示告警摘要、Trace ID、任务尝试/状态、时间线、结论、证据、审批和受限动作结果；加载、空、错误状态明确；只有授权测试角色可见相应操作。
- 验证方式：浏览器端到端验收。

### AC-06：测试身份、角色和资源授权有效

- 前置条件：本机测试用户与角色已初始化。
- 操作：以不同角色访问事故、证据、审批和测试执行接口，并尝试越权访问。
- 预期结果：服务端在每个入口校验身份、角色与资源归属；告警 payload 或 Agent 输出中的身份字段不作为授权依据；未授权请求不泄露数据且不产生副作用。
- 验证方式：权限矩阵集成测试。

### AC-07：处置仅能操作隔离的演示订单服务

- 前置条件：测试动作白名单、测试审批角色及执行器已配置。
- 操作：提交未授权、未审批、重复、取消、成功和验证失败的测试动作。
- 预期结果：执行器只向 Compose 中演示 order-service 拥有的受认证动作接口发请求，由 order-service 在服务端验证动作、资源、参数和幂等键并实施副作用；执行器不得绕过服务接口直接写数据库或容器。不挂载 Docker socket、不运行任意 Shell；执行前重验身份、权限、审批与幂等键，并记录执行、验证和回退审计。批准状态本身不授予执行权限。
- 验证方式：安全拒绝测试及隔离 Compose 端到端验收；验证 order-service 会拒绝未认证、越权、错误资源和重复幂等请求。

### AC-08：本地部署、恢复和演示可重复

- 操作：按仓库文档启动/停止本机测试环境，制造订单故障，查看告警和调查，并演练测试数据备份恢复。
- 预期结果：无需手动改源码即可启动；容器、健康检查、数据卷和运行时配置说明完整；重启后业务数据和任务状态符合预期；文档清楚标示本地测试用途。
- 验证方式：干净配置下 Compose 启动、端到端流程与恢复演练。

### AC-09：发布和知识上下文可在测试环境关联

- 前置条件：凭据可用时接入选定 Git/CI 和 Runbook 来源；否则通过可重复 fixture 验收数据流。
- 操作：回放发布事件、已知故障、Runbook 引用和相似/不相似告警。
- 预期结果：事故、任务、Trace 与发布/知识证据可互查；来源和时间可审计；没有来源数据时明确标记缺失，不伪造引用。
- 验证方式：集成测试与 fixture 回放。

### AC-10：20 例评测可重复执行

- 操作：运行现有 20 个已知根因案例及故障回放。
- 预期结果：报告逐例记录运行模式、检索证据、诊断、误处置建议与聚类结果；区分合成、mock 与 live；不把样本校验报告描述成模型准确率，也不虚构性能数字。
- 验证方式：可重复的本地评测命令及机器可读报告。

### AC-11：后续正式环境准备边界清晰

- 操作：查阅部署和运维文档。
- 预期结果：文档列出由本机测试迁往正式环境时需确认的运行平台、身份提供方、密钥注入、域名/TLS、网络、容量/SLO、保留合规、备份恢复、CI/CD、外部集成和逐项处置授权；不得声称这些生产集成已实现或验证。
- 验证方式：文档审阅；正式环境部署与操作在独立授权后另行规划。

## 边界与约束

- HolmesGPT API、Agent 和工具集继续使用 Python/FastAPI，并在现有 `server.py` API 边界扩展；不新建重复的 NestJS 控制面。
- NestJS order-service 是本机演示故障源，也是本机测试执行器可作用的唯一资源；不为它赋予真实生产权限。
- OpenObserve 保存日志、Trace 与前端错误；关系数据库只保存事故编排元数据和任务状态。
- 调查默认只读。测试处置必须由服务端授权并经隔离测试执行器执行。生产 Agent 计划、用户审批记录或本机 Docker 状态均不能隐式授权真实生产写操作。
- 数据库 schema/migration、`.env`/密钥、CI/CD 配置和正式发布属于需单独授权的边界；本 Spec/Plan 批准本身不替代这些授权。
- 不提交真实 token、模型 key 或数据库密码，不输出到日志/报告。
- 当前演示页面为静态页面；Plan 根据现有目录确定工作台落点，避免引入重复的大型前端栈。

## 待确认项与假设

- 正式生产平台、身份提供方、租户模型、SLO、保留期和合规要求以后续部署计划单独确认；不阻塞本机测试阶段。
- 本机测试用身份来源、测试动作白名单及失败回退策略需在 Plan 以现有服务能力收敛；只作用于可丢弃的演示数据。
- PostgreSQL schema/migration 需在执行前另行取得用户明确授权。
- 是否提供模型凭据、OpenObserve 只读凭据、Git/CI 与 Runbook 测试环境待确认；没有凭据时相应 live 验收标记为待外部条件，不可用 mock 冒充。
